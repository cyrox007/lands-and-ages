# Этап 9.4.1 — диагностика просадки FPS при панорамировании

## Что удалось подтвердить

Пользователь наблюдает заметную просадку при перемещении камеры и подгрузке новых секторов; смена сезонов почти не влияет на FPS. Скриншот показывает **25 FPS** и **83 из 130** запрошенных чанков. Это наблюдение с реального ПК, но без системного профиля CPU/GPU.

Код `world.gd` показывает две отдельные потенциально тяжёлые операции:

- При каждом перемещении примерно на одну клетку карты выполняется `_refresh_visible(false)`: переоцениваются видимые чанки, обновляется очередь, а ненужные меши отправляются в LRU.
- На каждом кадре `_create_chunk` **синхронно в основном потоке** вычисляет `Chunk.create_mesh`, включая цвета/маски шести материалов для каждой вершины, и `WaterMesh.create_mesh`. Бюджет времени проверяется **после** построения целого чанка, поэтому он не ограничивает продолжительность одного тяжёлого задания.

Профиль **программного OpenGL Mesa llvmpipe**, сохранённый в автоматической визуальной проверке 9.4 до исправления, показал на фиксированном маршруте камеры:

| Показатель | До исправления |
|---|---:|
| Построено чанков | 154 |
| Попаданий в GPU-кеш | 93 |
| Вытеснений из кеша | **108** |
| Пиковый оценочный размер кеша | **2,84 МБ** |
| Лимит памяти кеша | **12 МиБ** |
| Лимит записей кеша | **24** |

Это **не аппаратные FPS**. Однако статистика доказывает преждевременное вытеснение готовой геометрии из-за ограничения в 24 записи, когда запас заявленного бюджета памяти ещё велик.

## Исправление

Увеличен лимит записей LRU **24 → 96**, при неизменном ограничении оценочной памяти **12 МиБ**. Кеш по-прежнему хранит только невидимые готовые меши; при изменении физической ревизии устаревшие меши удаляются, а хранилище продолжает освобождать ресурсы при достижении ограничения. Цель — уменьшить перестроение при движении вперёд-назад по карте.

Добавлены раздельные CPU-таймеры создания мешей земли и воды. В диагностике Godot отображается время их построения за последний кадр. JSON маршрута камеры теперь содержит `ground_mesh_cpu_ms_total` и `water_mesh_cpu_ms_total` по каждой фазе и в сводке. Это **время синхронной генерации мешей**, а не GPU frametime; время вызовов движка и передачи данных GPU может остаться сверх этих показателей.

## Как сравнивать после исправления

Использовать **одинаковую карту, масштаб и маршрут камеры**. Встроенная кнопка тестирования 8.8 запускает девять фаз (370 кадров) и сохраняет JSON. Сравнивать число `cache_evictions`, `cache_hits`, `chunks_built`, p50/p95/p99, время `ground_mesh_cpu_ms_total` и `water_mesh_cpu_ms_total`. При сравнении аппаратных результатов отдельно учитывать Debug/Release и прогрев GPU.

Автоматический маршрут 8.7 и программный OpenGL 9.4 помогают подтвердить сокращение повторных построений, но результаты **не заменяют измерения на ПК с настоящим GPU**.

## Что остаётся возможной причиной

Увеличение кеша устраняет не все просадки: первый проход по новой области всё равно синхронно строит один или несколько мешей, а шесть PBR-покрытий плюс трипланарная скала нагружают GPU. Если после исправления падения останутся **именно при первом посещении**, следующим этапом следует профилировать и вынести CPU-вычисления мешей в управляемую подготовительную очередь без обращения к сцене из фонового потока, а затем проверить безопасную передачу готовых массивов GPU.

Переход на Vulkan не устраняет автоматически CPU-паузы построения геометрии и должен оцениваться отдельным сравнительным тестом.
